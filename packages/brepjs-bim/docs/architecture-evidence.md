# Evidence for the BIM architecture decisions

This note preserves the evidence behind the eight package-local ADRs. Start with [ADR-0001](adr/0001-independent-product-representation-and-placement.md) for the architectural direction and the [BIM glossary][glossary] for vocabulary. The [migration note](architecture-migration.md) holds integration acceptance criteria. No external project access or conversation history is required.

## Decision provenance

The records follow the root [layering][root-layering], [kernel/domain boundary][root-domains], and [identity][root-identity] decisions. The package is a prototype; breaking changes are permitted without compatibility aliases or a permanent facade. Extracting a recommendation into its own record does not accept it or claim it has shipped.

No identity enters CSG hashes; names, placement, and shape do not substitute for stable authored keys.                                 |

## IfcSign change spread

A previously reviewed IfcSign implementation touched 24 files for 412 additions and 66 deletions. Tests, documentation, class-specific mappings, and authoring rules explain part of that count. The consequential edits registered the same existing solid behavior again in disposal, Placement, validation, and adapters. The feature introduced no new Placement or disposal behavior. Of the 24 files, 18 were production source, five tests/fixtures, and one README; eleven production files added only one to four lines. The branch also includes an incidental schema-dependent property-writing correction, so not all spread is attributable to class extension. This historical example motivates the [extension acceptance scenario](architecture-migration.md#acceptance-scenarios); the repository's existing class-specific disposal and Placement show the underlying coupling. ### Evidence that must not be promoted into another defect

- A reported asymmetric Beam profile discrepancy remains focused authoring geometry work. The rectangle-profile `Position` import defect was fixed by #2273. It is not an outstanding prerequisite for the architecture. [#2273][pr2273]
- A third-party public-interface roof probe reported that supplying conventional `thickness` produced `IfcRoof` but changed native volume from `435223008.584494` to `480550651.800002` mm³, about 10.4148%. Exact takeover returned `EXACT_BODY_UNSUPPORTED_CATEGORY`. These are reported results, not rerun measurements for this documentation work. The repository source independently confirms that exact takeover rejects Roof and that civil routing lacks a roof entry. [Takeover][takeover], [routes][routes]
- Third-party projects reported submicrometre mesh deviations and a guarded planar localization correction. A historical self-intersection diagnostic was later identified as a checker false positive. This does not establish invalid native geometry. Local coordinates deserve a precision regression, but these records neither adopt a plane-snapping workaround nor claim local coordinates alone solve every tessellation problem.
- Other reported failures came from caller authoring or test infrastructure: doubled column translation, independently rounded nonplanar profiles, redundant dimensions that drifted from geometry, weak source guards, and stale grade receipts. Source zero-thickness features and invalid source-mesh volume evidence are source limitations. A circular-support tessellation report still needs an isolated reproduction before responsibility can be assigned.
- Historical third-party verification covered particular source inputs and measurement implementations. It does not establish passing results for this repository's current revision.

Takeover at the reviewed baseline also retains the caller's Body object and item container. It checks incoming duplicates and reuse of the target's parametric solid, but does not check all handles already owned by other document records. Those are source-observed enforcement limits, not a reproduced failure for callers obeying the documented exclusive-ownership precondition. [Takeover implementation][takeover]

### Overlapping-item coincidence: analytical counterexample

Families at the reviewed baseline measures a Body by summing item volumes, then compares that sum with the parametric volume and their combined union. Exact wall quantities instead measure the material union; the importer at that baseline also sums item volumes. Overlapping items are supported by an existing exact-wall test, and compound evaluation does not establish disjointness. [Coincidence][coincidence], [wall quantity measurement][wall-quantities], [overlap test][overlap-test], [compound evaluation][compound]

Consider two solids A and B, each of volume 1, overlapping by 0.5. Their material union has volume 1.5. A parametric candidate P of volume 2 contains both. The comparison at the reviewed baseline can observe `sum(A,B) = volume(P) = volume(union(A,B,P)) = 2` and accept P, although the material differs.

This is a source-derived analytical counterexample, assuming successful geometric operations with those values. It has not been run through the native kernel. It is neither a demonstrated downstream failure nor evidence of a performance regression. It justifies a native regression and a single definition of material measurement; it does not reopen the reported cases resolved by #2272.

### Standards basis

- [IfcWall rules](https://standards.buildingsmart.org/IFC/RELEASE/IFC4_3/HTML/lexical/IfcWall.htm) distinguish inherited entity constraints and legal type assignment from an application's internal class structure.
- [Spatial containment](https://ifc43-docs.standards.buildingsmart.org/IFC/RELEASE/IFC4x3/HTML/lexical/IfcRelContainedInSpatialStructure.htm) and [type relationships](https://ifc43-docs.standards.buildingsmart.org/IFC/RELEASE/IFC4x3/HTML/lexical/IfcRelDefinesByType.htm) have separate meanings and constraints.
- [Classification references](https://ifc43-docs.standards.buildingsmart.org/IFC/RELEASE/IFC4x3/HTML/lexical/IfcClassificationReference.htm) allow direct system references or supplied parent hierarchies. [bSDD guidance](https://technical.buildingsmart.org/services/bsdd/referencing-bsdd-in-ids-and-ifc/) describes version and URI mappings.
- The [buildingSMART validation service](https://technical.buildingsmart.org/services/validation-service/) separates STEP syntax, schema, normative rules, and industry practices. [IDS](https://www.buildingsmart.org/standards/bsi-standards/information-delivery-specification-ids/) specifies information requirements; it does not replace geometric comparison.
- [IFC4 Reference View](https://standards.buildingsmart.org/MVD/RELEASE/IFC4/ADD2_TC1/RV1_2/HTML/schema/views/reference-view/index.htm) leaves full parametric behavior with the originator. Preserving evaluated semantics does not promise native Family recovery.
